The Growing-Agent Pattern

Every S-agent is built the same way — so each one gets better run to run, on an Azure-Foundry-only, cost-optimized budget, with no GPU. This page is the why and the how. S2 (Moat) is the reference implementation.

§1 — The idea

Three lines everyone must hold

01

An agent is a policy grown inside a deterministic environment — not a prompt you call once.

02

One reward gates the agent now (the loop) and could train it later (ART) — the same function.

03

Every run writes a lesson to memory; the next run retrieves it. Skill compounds.

The claim

Investing is too large to one-shot. So we give the agent an environment it can't fabricate, a memory that remembers, and a reward — and let it grow. The growth is engineered, not hoped for.

§2 — Rationale

Why this pattern is good

Each property below is a deliberate engineering choice — and the reason judges and teammates should trust the output.

Grounded by construction
A hard gate rejects any fact not in the environment. The agent cannot hallucinate a number or invent a source — grounding is enforced.
The reward is deterministic
Same draft → same score, forever. Unhackable and reproducible — and safe to reuse as an RL reward later. No LLM-judge randomness inside it.
It compounds — cheaply
Each run's mistake becomes a lesson the next run avoids. Fewer iterations = lower token cost. Quality ↑ while cost ↓, no GPU.
One reward, two uses
The exact object that gates the loop is the future training signal. No wasted work, no divergence.
Uniform contract → parallelism
Six agents, one shape (three methods). Build S1–S6 in parallel, each testable, none blocking the others.
Human-in-the-loop is structural
Judgment fields stay drafts until a person confirms at a gate. Capital decisions never auto-fire.
Honest about signal
We separate process quality (now) from did-the-thesis-play-out (later) — and never confuse them.
Future-proof for ART
The lessons + high-score traces the memory accumulates are the training set. ART slots in with zero rework.
§3 — The constraint the team must understand

Why a Foundry-hosted model can't run ART

ART (OpenPipe's Agent Reinforcement Trainer) makes a model better by changing its weights with reinforcement learning (GRPO). Our contest gives us a hosted inference endpoint on Azure AI Foundry. Those two are fundamentally incompatible.

What ART requiresWhat a hosted Foundry model gives you
Open model weights you controlA closed, inference-only endpoint — weights never exposed.
Gradient computation + weight updates (GRPO)No gradient/weight access. You can only send prompts. Training on it is impossible.
A GPU + vLLM backend you drive during rolloutsA managed API, no GPU you own. ART on Azure means deploying an open-weight model to GPU compute yourself.
Sustained GPU hours for the runCheap per-token inference — the point of the scope. GPUs break it.
Contest fit✓ This is the given constraint — a Foundry LLM, called cheaply.
Don't confuse these

Azure does offer hosted fine-tuning (and reinforcement-fine-tuning on some models). That is a provider-run, model-specific, paid service — not running ART's open-weight GRPO loop yourself, and not "just use a Foundry LLM cheaply." A heavier path we deliberately do not depend on.

So where does "growing" come from?

The fast loop + memory — learning at inference time, by changing the context we feed the model (retrieved lessons, critique-driven revision), not the weights. Needs none of the four things above. Runs on a plain Foundry endpoint, today.

§4 — The difference to internalize

Two speeds of learning

Our pattern is the fast loop. ART is the slow loop — an optional, GPU-bound upgrade. Both optimize the exact same reward, so nothing is wasted.

The message

We do not need ART to ship a growing agent. The fast loop already makes every S better run-to-run inside the contest's constraints. ART is a slide that says "and here's how it scales further with GPU" — not a dependency, not a demo risk.

§6 — Memory

The knowledge graph: how each agent stores what it learns

Two tiers, kept distinct. A shared domain graph (companies, financials, theses, evaluations) that every agent appends to — and a per-agent lesson memory that each agent owns alone.

two tiersgraph
(Company)──has──(Statement/Metric)──sourced_from──(Provenance)      ┐
   └──has──(Thesis)──evaluated_by──(Evaluation)                     │ TIER 1 · SHARED domain graph
                         └──produced──(Lesson)                      ┘ (the candidate file materializes it)

Lesson.Id = "{agent}|{sector}|{trigger}"                            ┐ TIER 2 · PER-AGENT lesson memory
   e.g. "s2-moat|consumer_staples|UNCITED_SOURCE"                │ partition = agent · scope = sector
   fields: warning, learnedFrom, timesApplied, timesHelped, hitRate ┘ key = the mistake it prevents
  • Partition = the agent (s2-moat, s3-financials…). Each agent's memory is its own bucket.
  • Scope = sector. Retrieval is WHERE agent = me AND sector = this company's ORDER BY hitRate LIMIT k — bounded, so the prompt never floods.
  • Key = trigger (the mistake). Lessons upsert (keep stats) and each tracks its own hit-rate, so bad notes decay out.
ILessonStore — the whole contract (swap the backing, not the loop)csharp
interface ILessonStore
{
    Task<IReadOnlyList<Lesson>> RetrieveAsync(agent, features, topK);  // scoped, top-k by hitRate
    Task WriteAsync(Lesson lesson);                                    // upsert, keep stats
    Task RecordApplicationAsync(id, helped);                           // hitRate = helped / applied
    Task<IReadOnlyList<Lesson>> AllAsync();                             // GET /lessons inspector
}

The payoff

Because Retrieve / Write / RecordApplication are the whole contract, JSON → Cosmos is one environment variable (AGENT_COSMOS_CONNECTION) — no agent code and no loop code changes. An agent's evaluations feed the shared Tier-1 graph; its lessons stay in its own Tier-2 partition. That's why six agents learn in parallel without colliding, yet all build one company knowledge graph.

§7 — What you implement

The contract: three methods

The loop, memory and reward-shape come from the shared harness — you never touch them. Each agent implements only this.

IAgent — the whole jobcsharp
public interface IAgent
{
    string Id { get; }                       // "sN-name" — stable; your memory partition key
    Task<string> GenerateAsync(...);          // 1. produce a draft (Foundry model, or a mock)
    Reward Evaluate(string draft, ...);         // 2. THE REWARD — gates + graded + triggers  ← the crux
    Lesson? LessonFor(string trigger, ...);    // 3. a fixed mistake → a reusable, scoped lesson
}

Before you code — answer the five decisions

  • 1Environment — what can the agent NOT fabricate? (S3: the calculators · S2: the allowed sources)
  • 2Hard gates — the pass/fail rules that zero the score; name each with a stable trigger key.
  • 3Graded components — 3–5 quality dimensions in [0,1], weights summing to 1. Deterministic only.
  • 4Features — what makes a lesson relevant later? (at minimum Sector)
  • 5Lessons — for each fixable trigger, the scoped, conditional guidance to inject next time.
§8 — Non-negotiable

The invariants

These keep every S consistent. Break one and the agent stops being trustworthy — or stops being trainable.

  • Grounding by construction. The agent never invents environment facts; the hard gate enforces it.
  • The reward is deterministic. No randomness, no LLM-as-judge inside Evaluate.
  • One reward, two uses. The object that gates the loop is the training signal. Never fork them.
  • Drafts stay drafts. Human-judgment fields carry humanConfirmed:false until a gate.
  • Lessons are conditional & hit-rated. Scope every lesson; let the store decay the ones that stop helping.
  • Two signals kept apart. Process quality (now) ≠ thesis outcome (later).
  • Cost lives in the harness. Retrieval budget, stop-at-target, capped iterations, environment-does-the-math.
§9 — It works

What "compounding" looks like (S2)

Fresh memory, offline mock, two consumer-staples companies. Run 1 stumbles and fixes it; run 2 never stumbles.

RUN 1 · VNMiterations 2 · firstScore 0 (invented a citation → gate) · best 1.0 · LEARNED a lesson
RUN 2 · MSNiterations 1 · firstScore 1.0 (lesson injected up front) · best 1.0 · lesson hitRate → 1.0
Fewer iterations = lower token cost. Smarter and cheaper — with no weight training. That is the whole thesis, running.
